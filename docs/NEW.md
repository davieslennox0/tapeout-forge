## latch-reconcile branch (not yet merged to main)

- LATCH forward-feedback reconciliation (read-only on chain, no transactions/keys). Source: Nandout's vendored contracts/src/vendor/tapeout/lib/NetlistVM.sol (github.com/davieslennox0/nandout). Quoted evidence that forward feedback through LATCH.d is explicitly allowed by the real protocol design, not a Nandout-only interpretation:
  - Line 12-13 (file header): "与 web/src 里的 JS 仿真器逐位一致... 求值语义 state[t+1]=f(state[t],inputs)" ("bit-exact with the JS simulator... evaluation semantics: state[t+1]=f(state[t],inputs)").
  - Line 50: `uint256 d = _u24(nl, p); // d 是时序引用，允许指向靠后信号，但必须存在` ("d is a temporal reference, allowed to point to a later signal, but must exist").
  - Line 65: `require(nLatch == 0 || maxLatchD < outPos, "LATCH d out of range");` — `outPos` here is the FINAL signal count after scanning the WHOLE netlist (maxLatchD is accumulated across the entire single pass in `analyze()`), not the latch's own position at parse time. This is the actual bound: d must be < total signal count, not < the latch's own index.
  - Lines 216-226 (`_depth`) and lines 359-363 + 371-374 (`_execute`): LATCH output = the OLD stored state (set immediately, pass 1); `d` is sampled and written back as next-state AFTER the full pass (`_execute`'s explicit "第二遍"/"second pass" comment: "LATCH 新状态取本周期 d（d 可指向靠后信号 → 反馈回路）" = "LATCH's new state takes this-cycle's d (d may point to a later signal → feedback loop)").
  - Line 400: `(bytes memory subNew, bytes memory subOut) = ICPU(cpu).step(cid, subState, subIn);` — gives the real step() ABI shape: `step(uint256, bytes, bytes) returns (bytes, bytes)`.

- Deployed-contract verification (read-only, X Layer RPC https://rpc.xlayer.tech): computed the real keccak256 selector for `step(uint256,bytes,bytes)` = `0xe8281a1a` (keccak implementation sanity-checked against the well-known `transfer(address,uint256)` = `0xa9059cbb` first). The on-chain address `0x57F319CF056F72F48cF1dbb670F2A3DB007Aa355` ("OrderGuard") turned out to be a 295-byte BEACON PROXY, not the real logic — it calls `implementation()` (selector `0x5c60da1b`) on beacon `0xf70d1ed4f62cf3780157b0b421b7e2f45bd0991c`, which resolves to the real implementation at `0x977f217887e085d298cb3819cdad5a0ee35f29b2` (12,562 bytes). This is a new architectural fact worth keeping: processor addresses on X Layer are beacon proxies, not the logic contracts themselves — any future bytecode-level check against a processor address needs to resolve the beacon first.
